## fn_8028C6B8 (animation/goals/tu_8028C6B8), 99.916%, 653/653 insns, 9 slots differ -> 8

- NEW: one of the 9 slots is a real control-flow bug, not allocation. Retail's switch dispatch does
  `cmpwi r0,0; blt <end>; b <case 0 body>` (values 0 and 1 share the case-0 body), ours `beq <case 0>; b <end>`.
  Add `case 1:` to the `case 0: case 20:` group. Scored: 9 -> 8 differing slots (variant `c6b8_v0_case1.cpp`).
  Too small for a near-miss commit alone (0.15 points), but it must go in with the next fix.
- The remaining 8 slots are the 4 zero-valued slot writes: retail `li r9,off; stwx v,r30,r9`, ours `li r0,off; stwx v,r30,r0`
  (cases 9, 11, 22 and the C8==0 arm of 19). Both sides have r0 dead at that point, so it is a register-CLASS choice, not liveness.
  Mechanism (regclass.c record_address_regs, PLUS of two REGs): if one operand is pointer-flagged it is the base and the other
  the index (INDEX_REG_CLASS = GENERAL_REGS, so r0 is first choice); if NEITHER is pointer-flagged each operand gets half its
  cost as a base, GENERAL_REGS is penalised (r0 is not in BASE_REGS) and the constant pseudo's preferred class becomes
  BASE_REGS -> r9. So in retail the base pseudo at these four stores was NOT pointer-flagged. Pointer flags come from
  mark_reg_pointer: pointer-typed locals/params (expand_decl, assign_parms) and ADDR_EXPR results; a cast to int is a no-op on
  the same pseudo and keeps the flag. This agrees with RE4's note (PATTERNS "ProDG tricks" 4: offset in r9 means an integer base).
- Tried, all still 8 slots: SetIZ with `int a` / `unsigned a` parameter and `(int)ang` actual; `int ia = (int)a;` inside the
  helper; the Z helpers taking `Unk8028C6B8_Angles&`; calling the Z helpers with `&x->m734` instead of `ang`; a separate
  `int iang = (int)ang;` local passed as an extra parameter. All of these collapse back onto the flagged pseudo (cse replaces
  the copy by the oldest equivalent register).
- Not tried yet: a base that never was a pointer pseudo (e.g. an `int` member or an `int` result of a non-inline call), or
  checking in the `.lreg` dump (`Register N pref BASE_REGS`) which class our constant pseudo gets; a `-dg` look at whether the
  `li` is a reload (REG_EQUIV constant) or an allocated pseudo would settle whether class or reload order decides.

## fn_8028D200 (animation/goals/tu_8028C6B8), 99.978%, 185/185, 4 slots: two float slots swapped (0xA8 <-> 0xC0)

- Mapped the frame from the asm. Retail: len@0xA0, Recip's x@0xA8, Scale's r@0xB0..0xBC, Scale's s@0xC0.
  Ours: len@0xA0, s@0xA8, r@0xB0, x@0xC0. So TWO things differ, not one: (1) the Recip frame block comes before Scale's in
  retail; (2) inside the scaling helper retail has r (local) BEFORE s (float parm), ours s before r. A float parameter
  under -ffloat-store gets its slot in assign_parms, before any body local, so in retail `s` cannot be a parameter of the
  function that owns `r`: the scale factor is a local declared after the result vector, or the result vector is not a local
  of the helper. Any candidate must satisfy both (1) and (2); the previous worker's variants (named inv local, parameter
  order, Recip result local, open-coded scaling) only move one.
- Background (from integrate.c / function.c, 2.95): an inline's frame is ONE BLKmode block allocated lazily at the first
  virtual-stack-vars reference (copy_rtx_and_substitute), i.e. after the arguments were expanded; assign_stack_temp reuses a
  free slot only with the same mode and size >= request (SFmode slots are never combined, BLKmode ones are); the frame grows
  upward, so the earlier allocation has the lower offset; statement-level temps (inline parm slots, inline frame blocks)
  are freed at the end of each statement (expand_end_target_temps), block locals at the end of their block.
