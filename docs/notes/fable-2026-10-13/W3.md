What the compiler does (read from `cc1plus -dS -dR -dl -dg`, dumps in scratchpad/dump/):
- One SF pseudo (r132) holds 0.6f for BOTH stores: cse folds both constant-pool loads to the CONST_DOUBLE and merges them,
  so the pseudo dies at whichever store is LAST in RTL order. sched1's rank_for_schedule prefers the store whose source
  register dies (INSN_REG_WEIGHT -1), then LUID. RTL order a,b,c (declaration order) => c-store first (what we get).
- For retail's a, c, b with one shared pseudo the RTL store order would have to be c, a, b (or c, b, a) while the frame
  slots stay a<b<c; slots are assigned at declaration under -ffloat-store (expand_decl -> assign_temp), so the only
  plain-source way is "declare a, b; declare c = 0.6f; assign a and b afterwards" -- unnatural, and `b` must still fold
  to a constant in the arm (`c = b` with non-const b reloads from memory: +1 insn). Alternative explanation that also
  gives a, c, b: two distinct 0.6f pseudos (both dying at their own store) sharing f0 -- needs cse NOT to merge the two
  pool loads, which I could not produce (same ebb, pool loads fold to the same CONST_DOUBLE).
- cse does NOT forward a float store to a following load under -ffloat-store (cse_insn drops src_elt for FLOAT_MODE MEM
  dests), so `float c = a;` always reloads `lfs f13,8(r1)` (+2 insns). Only const-folded forms keep one lfs.
