## fn_801971B8 (game/tu_80194D44) 99.99% -> 100% (MATCH)

Symptom: identical 143 instructions, only the reciprocal float's slot differed (retail 0x74, ours 0x7C). Ten earlier
"reciprocal/local/helper" forms had failed (NEARMISS.md).

Frame: 0x50 f (-ffloat-store local), 0x58 q (BLK 16), 0x68 `float s = f`, 0x70 the lerp inline's `s` parameter,
retail 0x74 inv, 0x78 n (squared length, stored then reloaded into f1 for sqrtf).

Mechanism (GCC 2.95 integrate.c): when an inline is expanded, its WHOLE frame (float params under -ffloat-store, its
float locals, nested inlines' frames) is allocated as ONE BLKmode stack temp of the callee's frame size, 8-aligned and
rounded to 8, at the first reference to the callee's frame pointer. A separate `Lerp(q, pa, pb, float s)` inline has a
4-byte frame -> an 8-byte block at 0x70..0x77, so nothing in the caller can ever land at 0x74. The caller's `float n`
and `float inv` then go to 0x78/0x7C. A 4-byte slot inside such a gap can only belong to the SAME inline's frame.

Fix: one inline does the lerp AND the normalisation; `inv` is its local and the squared length is the parameter of a
nested float-parameter inline (its frame = the next 8-aligned block inside the outer frame):

    inline float InvSqrt(float n) { return 1.0f / sqrtf(n); }
    inline void Nlerp(Q* q, const float* pa, const float* pb, float s) {
        ...lerp into q...
        float inv = InvSqrt(q->m0*q->m0 + q->m4*q->m4 + q->m8*q->m8 + q->mC*q->mC);   // inv at +4, InvSqrt frame (+n) at +8
        q->m0 *= inv; ...
    }

Inline frame layout = param s +0 (assign_parms), inv +4 (expand_decl, allocated BEFORE its initializer runs), nested
inline frame +8 (BLK, 8-aligned) = 16 bytes -> 0x70/0x74/0x78. `float inv; float n = ...; inv = 1.0f / sqrtf(n);`
(inv declared first) also matched; `float n = ...; float inv = ...;` inside the inline gives n +4, inv +8 (4 slots off).

General rule for the next matcher: when retail has a 4-byte float slot in the 8-byte gap right after an inline's float
parameter slot, that slot is a local of the same inline (or of the same enclosing inline), not of the caller. Conversely,
two consecutive 8-aligned float slots are two separate inline frames (or a frame plus a BLK local).

Verified: VERIFY PASS, 21096 functions at 100% (baseline 21095). Commit `match(game/tu_80194D44.cpp): fn_801971B8 [20/39 funcs]`.

## fn_801C6D88 (game/tu_801C6D2C) 98.36%, NOT finished (lead stopped the pass)

Diff: 148 vs 150 instructions, same code; only the x < 0 arm's slots differ. Retail: condition AbsF frame 0x18, then-arm
LerpATB frame 0x20..0x2F (a,t,b), else-arm AbsF#2 at 0x30 and LerpATB#2 at 0x18 (a 0x18, t 0x1C, b 0x20). Ours: identical
except LerpATB#2 reuses 0x20 (the freed then-arm frame), plus a 2-instruction trailing `stfs/lfs` of the result (0x38)
that retail does not have in the random-branch tail.

Why ours cannot reach retail with separate AbsF/LerpATB inlines (measured with scratch experiments, scratchpad/W11/t2.cpp,
t3.cpp, compiled with the game flags):
- An inline's frame block is freed at the end of the full statement that contains the call (free_temp_slots): two inlines
  in consecutive statements reuse the SAME block (e1: both `A()` params at 0x10). Two inlines in one expression get two
  blocks (s4). A nested inline's frame lives inside the outer inline's block (s5: N frame 0x10..0x27 holds x at +0 and the
  LerpATB frame at +8; the following statement's A() reuses 0x10 with the whole 24-byte block, no split).
- An inline expanded inside an `if` CONDITION is NOT freed until the whole if statement is over (e3/s2/s3: the condition's
  A() frame stays allocated through both arms; s2: the statement after the if reuses it). This is CLEANUP_POINT_EXPR's
  preserve_temp_slots moving the condition's temps one level up.
- A freed BLK block is reused whole by any request <= its size (no splitting seen); an SF local never reuses a freed BLK
  block (mode must match), it always takes a fresh 4-byte slot (e1: s at 0x18 right after the freed 8-byte block).
- Memory (float, -ffloat-store) parameters of an inline are evaluated AFTER the callee frame block is allocated, in
  parameter order (e2: L frame 0x10 before the nested A frame at 0x20 even though A(v) is L's argument).
- SF locals are 4-byte stride (t1: 12,16,20); only BLK blocks are 8-aligned/rounded.

Consequence for fn_801C6D88: for LerpATB#2 to land at 0x18, a FREE block of >= 16 bytes must start at 0x18 when the else
arm is expanded, while the then-arm's LerpATB got a fresh block at 0x20. The only shape consistent with all rules is a
24-byte inline frame at 0x18 = {float x at +0 (the value fabs reads in the condition), nested LerpATB frame at +8 (the
then-arm)} that is freed before the else arm is expanded, after which LerpATB#2 takes the whole 24-byte block and AbsF#2
gets a fresh 8-byte block at 0x30. I did not find the C++ shape that yields it: the obvious candidates all fail because the
condition's abs and the then-arm lerp must share one inline frame while the else arm must be OUTSIDE it (candidates: an
inline `Pos(float x)` holding the x < 0 test + then-lerp puts the else arm inside too; computing the then-arm first in
a local puts its frame at 0x18, not 0x20). Untested ideas: (a) a helper inline taking x that returns the then-lerp or a
sentinel, with the caller doing the negative arm when the sentinel comes back (odd source, but gives exactly this frame
shape); (b) the trailing stfs/lfs pair in the random branch suggests the function result is a `float r` local there;
check whether retail's tail is `return r` through a local only in that branch. Do not retry the ~12 forms in the file's
