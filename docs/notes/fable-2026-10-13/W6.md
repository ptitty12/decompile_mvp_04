### fn_801852A4 (game/tu_8018423C) 99.6% -> MATCH (96/96), 1 variant round; commit 7afa3b94 on work/hard-04 (VERIFY PASS, 21095 vs 21094 baseline, no regressions)
Symptom: instructions identical, only frame slot offsets differ (the parked note listed the retail slots).
Retail allocation order, read off the stfs/lwz offsets (frame grows upward, so ascending offset = allocation
order): 0x20 Mul's Vec3 operand, 0x30 Sub's inline frame (r local) and later the `*out = Add(...)` return
temporary, 0x40 Mul's return temporary, 0x50 Mul's inline frame {s, r}, 0x68 Add's inline frame {r}.
Ours (single nested expression `*out = Add(*a, Mul(Sub(*b,*a), *t))` with `Mul(Vec3 v, float s)`):
0x20 Add return temp, 0x30 Mul return temp, 0x40 v copy, 0x50 Sub frame, 0x60 Mul frame, Add frame reuses 0x50.
Fix (variant 1 of 5, exact match):
```

*out = Unk801852A4_Add(*a, Unk801852A4_Mul(d, *t));    // Mul now takes const Unk80183918_Vec3&
```
Also tried (all worse): named d + by-value Mul (107 insns: extra 3-word copy d -> invisible-ref slot);
`Vec3 d; d = Sub(...)` (105 insns, two copies); `Vec3 m = Mul(d,*t); *out = Add(*a, m)` (96/96 but 26 slots off).
GENERAL (compiler behaviour, verified here):
- PowerPC EABI (V.4 ABI, rs6000 `function_arg_pass_by_reference`) passes EVERY aggregate by invisible reference,
  POD or not. So an inline `f(Vec3 v)` by-value parameter is NOT part of the inline function's frame block: the
  caller allocates a separate 16-byte `assign_stack_temp` slot for the copy before expanding the argument into it
  (`store_expr(arg, slot)`), and the argument's own inline frame comes after that slot. A `const Vec3&` parameter
  allocates nothing. "By-value Vec3 inline params allocate extra temps" in PATTERNS is this rule.
- An inlined function's locals live in ONE block (`assign_stack_temp(BLKmode, DECL_FRAME_SIZE)`), allocated at
  the first reference to its frame and freed at the end of the inline expansion when the first reference happens
  inside the inline's own binding level (locals only). An inline with a memory parameter (-ffloat-store float
  parameter `float s`, or a struct passed by hidden reference and copied) references its frame while the
  parameters are stored, before the inline's binding level is pushed, so that block stays live to the end of the
  enclosing statement (retail's Mul frame 0x50 was not reused by Add's frame; Sub's frame was reused).
- `*out = Add(...)` for a struct-returning inline always goes through a return temporary + 3-word copy; that
  temporary is `assign_temp`'d at the START of the statement, so a freed block from a PREVIOUS statement is what it
  reuses (exact-size first). Splitting a nested expression into `Vec3 d = Sub(...); *out = Add(..., Mul(d, ...))`
  is therefore the lever to move the return temporary to a lower slot. Both statement forms give the same
  instructions; only the frame offsets move, so score with rv.py/score_variants, not by eye.
