## fn_802C0050 (game/tu_802BF974): 97.54% -> 100% (MATCHED)

Near-miss note said: instructions identical, only the callee-saved registers of a0/a3/a4/a5 permuted

What fixed it: the float parameter is declared BEFORE a3/a4/a5:
    int fn_802C0050(int a0, float* p, float* q, float f, int a3, int a4, int a5)
instead of `(..., int a3, int a4, int a5, float f)`. The ABI is unchanged (GPR and FPR args are numbered
independently), but the mangled name changes, so symbols.txt was renamed with
`tools/scout/rename.py game/tu_802BF974.cpp --write` (fn_802C0050__FiPfT1iiif -> fn_802C0050__FiPfT1fiii).
All of `f` at position 1, 2, 3 or 4 match; `f` after a3 does not. I chose "after q".

Why (read from the allocator, `cc1plus -dg -dl` + `-dS`):
- lreg dump: a0, a3, a4, a5 all "used 4 times across 83 insns" -> exact priority ties ->
  global.c allocno_compare falls back to pseudo-number order (a0 first) -> a0 gets the highest free
  callee-saved register (r29), then a3, a4, a5.
- REG_LIVE_LENGTH after sched1 = number of insns from the pseudo's defining insn (inclusive) to the insn
  where it dies (inclusive), summed over blocks. Verified on a micro test (scratch w10q/t/t1.cpp): block 0
  copies were scheduled 7,9,11,5 and lengths came out 18 vs 22 exactly by that count.
- The -ffloat-store spill of a float parameter (`stfs f1,8(r1)`) is emitted by assign_parms at the
  parameter's declaration position. In block 0 sched1 keeps the priority-0 parameter copies in LUID order,
  so declaring `f` before a3 puts the stfs one insn before the a3/a4/a5 copies -> their live length is 82
  while a0 stays 83 -> priority 8*10000/82 = 975 > 963 -> a3, a4, a5 are allocated first (r29, r28, r27)
  and a0 last (r26). Retail's post-sched2 order (stfs BEFORE the a3 copy, ours after) was the tell.

GENERAL RULE (new, for PATTERNS): when callee-saved registers of equal-ref parameters are permuted and a
float parameter is present, move the float parameter in the declaration (mangled name changes, keep the
ABI). Each parameter copy or spill emitted earlier shortens the live length of every later parameter by
one insn; a one-insn difference is enough to break the tie. Tell: in retail the `stfs f1,N(r1)` sits
between the GPR copies, in ours it is after them (or vice versa).

Analysis (cse.c cse_end_of_basic_block): the chain of `if (a == K) { ... }` blocks is one extended basic
block because every `bne` to the next test label has LABEL_NUSES == 1 and no label between -> AROUND path
entries; the ebb only ends at a CODE_LABEL reached by scanning, at a NOTE_INSN_LOOP_END (cse1 runs
before loop), or when path_size reaches PATHLENGTH-1 (= 9 entries). Ours: the ebb containing both 0x4A
compares starts at the 0xC test (the two `bne .L_CEC` of the first test are unfollowable because the shared
`li r3,1; blr` label lies between) and has only 8 entries at the second compare, so it is CSE'd. Retail
needs the ebb to end between the two compares: either the ebb must start two tests earlier (9 entries used
up by the first 0x4A's bne) or a barrier must sit between them.
Tried: wrapping each of the 13 `if (a == K) {...}` blocks in `do { } while (0)` (13 variants, scratch
w10q/v_2ccc.txt): no variant fixed it; wrapping blocks 0x10, 0x28, 0x4A(first), 0x4A(second), 0x5A left
the score at 29 slots, wrapping any other block made it worse (79 slots: the loop notes changed the
block layout). So the LOOP_END-note barrier does not end the ebb here (or the AROUND jump over the body
skips the note). Next ideas (not tried): make the first test's `bne` followable so the ebb starts at the
function entry (e.g. write the first test as `if (a == 0x10 && p->y == 2) return 1;` or give the first
block a different shape so the shared return label is not between the bne and its target); or make the
0x3F/first-0x4A blocks `switch (b)` so their inner compares consume path entries; or spell the second 0x4A
test on a re-read `p->x` through a volatile view (fresh pseudo, no CSE) if the lwz is tolerated (retail has
