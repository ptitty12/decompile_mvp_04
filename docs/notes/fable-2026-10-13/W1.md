### fn_802A1790 (animation/goals/tu_8029EE50): 99.58% (378/379 insns, frame 304 vs 312) -> MATCH (379/379)

Three independent fixes, found by reading the diff rather than permuting:

1. Instruction count (ours 378, retail 379). Retail: `cmpwi r3,2; bne ->li r3,17; li r3,12; b epi`. Ours hoisted
   `li r3,12` above the branch and cross-jumped `beq epi; li r3,17` with the function's final tail. Cause: the
   source had `if (r == 2) return 0xC; return 0x11;` INSIDE the `if (p->m36C == 0) {}` block plus another
   `return 0x11` at the end. The `return 0x11` directly after the diamond is "an else arm that starts with a set
   of r3", so jump.c hoists (RE4 rule 11). Fix: make the else part a real `} else { ... }` and keep ONE
   `return 0x11` after the if/else; the `bne` then threads to the shared `li r3,17` and nothing is hoisted.
   General: when retail has `bne Lret; li r3,K; b epi` and ours has `li r3,K; b Lcrossjumped`, look for a
   duplicated `return K2` statement; the original had a single shared return after the if/else.

2. Compare load order at the tail: retail `lfs f13,m720(r30); lfs f0,f@8(r1); fcmpu f0,f13; cror so,eq,lt`
   (m720 loaded first, f compared first). Ours loaded f first. `!(m720 >= f)` swaps the loads but also the
   fcmpu operands/cror (23 vs 24 slots, not it). Mechanism: with -ffloat-store the parameter `f` is a stack
   MEM, and emit_cmp_insn force-loads op0 then op1, so m720 can only be loaded first if it reached the
   compare already as a pseudo. An inline accessor does exactly that (its return value is a pseudo, never a
   float-store slot):
       inline float Unk802A1790_M720(Unk80270BA0_X* x) { return ((Unk802A2604_Player*)x)->m720; }
       if (!(f <= Unk802A1790_M720(x))) ...
   General: "retail loads the member before reloading the spilled float parameter, compare order unchanged"
   = the member was read through an inline getter. Volatile view, `const float&`, `(float)` cast and `* 1.0f`
   all compile to the plain order.

3. Frame (+8) and three slot offsets: Probe's by-value float `h` at +0xE8 (reusing the operator+ result's
   slot) instead of retail +0xF8, the later `Vec3 v` at +0x58 (reusing Probe's param copy) instead of +0x68,
   eps/len 4 bytes low. In retail those temporaries are still in use when h and v are allocated. The probe
   was NOT an inline with by-value params in the original; written out in the body it matches exactly:
       Unk802A1790_V3 pv = a + Scale(Scale(Dir(ang), f), 0.35f);
       float h = 0.0f;
       fn_80191068(p, &pv, 0, &h, lbl_8061E858, lbl_8061E85C);
       if (!(h <= lbl_8061E854)) { ... }
   A named local `pv` is a keep=1 temp that lives to the end of the enclosing block (so the if-body's `v`
   cannot take its slot -> +0x68), and `h` declared after the full-expression statement gets a fresh slot above
   all the (freed, but never reused: different size class) expression temporaries. Also tried (all worse or
   equal): V3 with an empty destructor (no change, 21 slots), Scale/operator+ returning via a 3-float ctor
   (75 slots), Probe with `h` as its own local (21), Probe taking `const V3&` + local copy (132, +3 insns).
   The RE4 "cleanups keep temps alive" theory was wrong here: the dtor variant changed nothing.
