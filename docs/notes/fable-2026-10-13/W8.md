## General findings for PATTERNS

- Store-order near-misses: run the sched dump instead of permuting. `cc1plus -dS` writes `x.i.sched`/`.sched2`;
  the "Ready list (t = N)" line lists ready insns with the one picked LAST in the line, and the
  "scheduling visualization" table gives the issue order per cycle and function unit (lsu/iu/fpu...).
  The visualization's insn numbers can be matched to `[reg+off]=reg` to read off store order directly.
- Shared-constant stores: the earlier store in source order is the NON-dying one and goes last in the block
  (weight 0 vs -1). To put a constant's store at a given position, write the OTHER store of that constant first.
- Equal-weight stores keep source order through sched1; sched2 then only hoists stores whose source register
  is redefined later in the block (anti-dependence lengthens their path). Everything else stays in source order.
- Every variant that fixes the order of a few stores can re-rank local-alloc (the `li` hard registers):
  check that the constants' registers survive before trusting a store-order fix.

## Tooling / environment notes for the lead

- The scratchpad directory is shared by every worker spawned from the same lead session (other workers'
  files appeared in my `scratchpad/q`). rv.py's `QDIR/rvtmp` is rmtree'd on every run, so two workers using
  the same QDIR clobber each other. Use a per-worker QDIR (I used `scratchpad/W8`).
- `taskkill //PID <bash pid> //T` on the Git-bash job did not find the process; a PowerShell
  Get-CimInstance walk by command line did. Be careful: a filter on the function name also matches the shell
  running the kill script.
